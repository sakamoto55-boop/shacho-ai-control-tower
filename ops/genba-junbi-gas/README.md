## 1. Apps Script の失敗通知は、どちらも対応不要だった

| スクリプト | 関数 | 実行間隔 | 失敗 | 判定 |

エラーは `We're sorry, a server error occurred.` と `Exception: Service error: Drive`。
どちらも Google 側の一時障害で、スクリプトの不具合ではない。

**以前「失敗が続くとトリガーが自動停止する恐れがある」と伝えたが、これは過大評価だった。**
`processInbox` は毎分実行で1日約1,440回。8/21の失敗2回は失敗率 0.14% にすぎない。

実害も無い。`processInbox` は Drive エラーが出ると `DriveApp.getFolderById` の時点で中断し、
写真を1枚も掴まないまま終わる（失敗は1秒で終了しており、この経路と一致する）。
写真は受信箱に残り、60秒後の次回実行で処理される。取りこぼしは発生しない。

**対応不要。** 通知が煩わしければ Apps Script の失敗通知設定を日次サマリに変えるだけでよい。

# 台帳の重複と滞留の修正 2026-09-25

社長指摘：「台帳が重複している」「今日までのは一旦クリアにしたい」
「事務員が対応しているのに台帳に記載されて行って永遠にたまっていく仕組みになっている」。

**前提：8月に用意した修正4件は本番へ未反映だった**（本番ソースを取得して確認済み）。
今回の修正と合わせて1回で貼れるよう、`after/` は4件＋今回分をすべて含んだ状態にしてある。

## 調べて分かったこと

台帳 76行（未作成6・受渡済み70）。

**重複は8組16行。全て 2026-08-31 00:46〜00:48 に登録された側が重複。**
その8行だけ `requestSource` が `LINEWORKS 自動取込`＝受信箱画面の「登録」ボタン経由。
原因は `コード.gs` の `registerIntakeItem` に昇格済みチェックが無かったこと。
`manifestAutoPromote` は `promotedManifestId` を見て二重登録を防いでいるが、
画面から手で登録するとこの目印を無視して素通りする。受信箱には
「同じ現場名・近い日付の依頼が既にあります」という警告が出ていたが、止める力は無かった。

**滞留の原因は `buildChecklist` の条件。**
`!neededDate || neededDate <= addDays(today, 3)` なので、必要日を過ぎた行は
条件を満たし続ける。事務員が現物を用意し終えても、台帳の行は誰かが手で
「受渡済み」にしない限り「期限超過」として毎朝ずっと通知に出る。
70行が受渡済みなのは履歴が「登録」のままなので、過去に手でまとめて書き換えたと見られる。

## 入れたもの

**入口を塞ぐ**（`コード.gs` `registerIntakeItem`）
昇格済み（`promotedManifestId` あり）の依頼を画面から登録しようとすると
409 で止める。`forceRegister: true` を渡した時だけ通す。

**新規 `LedgerCleanup.gs`** — Run の前に必ず Preview がある。

| 関数 | 用途 |
|---|---|
| `ledgerStats()` | 現状確認（件数・重複数・未完了の最古） |
| `ledgerDedupePreview()` / `ledgerDedupeRun()` | 重複削除。依頼文＋必要日が同じ行を、**最も古い1行だけ残して**削除 |
| `ledgerCloseUntilTodayPreview()` / `ledgerCloseUntilToday()` | 今日までの未完了を受渡済みに |
| `ledgerCloseUntilYesterday()` | 昨日以前だけ。**今日必要の依頼は残す（推奨）** |
| `ledgerAutoClosePreview()` / `ledgerAutoCloseRun()` | 必要日を過ぎた行を自動で受渡済みに |
| `ledgerAutoCloseInstallTrigger()` | 上を毎朝6:30に動かす（7:30の通知より前） |

猶予日数は設定シートの `LEDGER_AUTO_CLOSE_DAYS` で変更可（未設定なら1日＝必要日の翌日に閉じる）。
必要日が空の行は登録日を代わりに使うので、日付なしの行も溜まり続けない。
閉じた行には履歴が残る（`by: 自動クローズ` / `summary: 必要日からN日経過したため受渡済みに変更`）。

## 実データでの検証結果

本番の台帳76行をそのまま使って手元で流した結果。

```
実行前   76行  未作成6 / 受渡済み70  重複グループ8件  未完了の最古 2026-09-18
  ledgerDedupeRun()          → 8行削除（残り68行）
  ledgerCloseUntilYesterday() → 3件を受渡済み
実行後   68行  未作成3 / 受渡済み65  重複グループ0件  未完了の最古 2026-09-25
翌朝6:30 ledgerAutoCloseRun()  → 残り3件も自動で受渡済み
```

## 実行順（推奨）

1. `コード.gs` `MorningBrief.gs` を `after/` の内容に差し替え、`LedgerCleanup.gs` を新規作成して保存
2. `ledgerStats()` … 実行前の数字を控える
3. `ledgerDedupePreview()` → 内容を確認 → `ledgerDedupeRun()`
4. `ledgerCloseUntilYesterday()` … 今日の依頼を残す場合。今日の分も消すなら `ledgerCloseUntilToday()`
5. `ledgerAutoCloseInstallTrigger()` … これ以降は自動で片付く
6. `ledgerStats()` … 結果確認

## 判断が要る点

自動クローズは「必要日を過ぎた＝現場が受け取って作業済み」と見なして閉じる。
実際には用意されなかった依頼も閉じてしまう可能性はある。
ただし現状は「期限超過」として毎朝出続けた末に誰も見なくなっているので、
閉じた方が実態に合うと判断した。厳しくしたい場合は `LEDGER_AUTO_CLOSE_DAYS` を
3 や 7 に設定すれば、その日数だけ通知に残る。
